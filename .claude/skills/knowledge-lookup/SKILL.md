# Knowledge Lookup

## Overview

`scripts/knowledge` is one query surface over two things: `docs/knowledge/`, the harvested corpus, and
`docs/product-spec/appendix-c-consolidated-normative-requirement-index.md`, the 645 canonical requirement
IDs across 19 subsystems that the corpus is indexed by. It is a thin bash wrapper over the C# tool in
`tools/Knowledge/`; if the wrapper is unavailable (Windows, no bash), the same command is

```bash
dotnet run --project tools/Knowledge -- --gaps RETRY
```

One executable, three commands: the query CLI (the default), `scripts/knowledge verify-structure` (the
blocking gate that keeps the two trees apart) and `scripts/knowledge drift` (the hand-run staleness report).
A first argument of `verify-structure` or `drift` selects the subcommand; to search the corpus for either
word, use `--grep`. `--root DIR` points any of them at another checkout — which is how you query a sibling
SDK's fuller corpus for comparison (`scripts/knowledge --root ../ruby-sdk --role design --req RETRY-5`).

**Read this first — what the corpus holds today.** `docs/knowledge/harvested/` is **seeded, spec role
only**: 960 entries in 26 topics, copied mechanically from `ruby-sdk@5b17395` because `docs/product-spec/`
here is byte-identical to Ruby's (every sha in `harvested/SOURCES.md` was re-verified against this
checkout). **The `design` role (`docs/sdk-design-dotnet/` 00–09) and the `styleguide` role
(`docs/styleguide/csharp/` 01–15 + README) are pending a harvest** — no `knowledge-harvest` run has happened
in this repository. Until one does:

- `--role design`, `--role styleguide`, every `--chapter N` query, and the styleguide-derived topics
  (`csharp-idioms`, `naming-conventions`, `testing`, `assertions`, …) return nothing (exit 1). Read the
  design chapter or the styleguide chapter directly; the `Today` column of the audit table below says which.
- `--section conflicts` returns nothing: a Conflicts entry records a design-vs-styleguide contradiction, and
  neither side has been harvested.
- `notes/` is empty. The Ruby notes record Ruby implementation findings and were not carried over.
- Everything ID-first works: `--req`, `--prefix`, `--gaps`, `--prefix-info`, `--coverage`, `--phase`.

Every entry is one bullet plus a `<sub>` line, and a stable key — `<topic>/<8 hex>`, printed after the
section name. The `<sub>` usually carries role, source path, line range and sha, which is the citation a
test-file header or deferral note needs; a Conflicts entry carries two sources and no sha, and a note carries
a manual `sha:` marker. Copy what is there.

**Two trees, one query surface.**

| Tree | Holds | Rule |
|---|---|---|
| `docs/knowledge/harvested/` | What the source documents say. Roles `spec`, `design`, `styleguide`. | Generated by `knowledge-harvest` (today: seeded). **Never hand-edit it.** A `<sub>` sha digests the whole source file, not the entry, so your edit changes no sha and the next harvest deletes or duplicates it. |
| `docs/knowledge/notes/` | What the implementation found. Role `review`, a manual `sha:` marker. | Hand-written. Small by design — a note earns its place only by overriding a harvested rule. |

**How to read a result:** a role of `spec`, `design`, or `styleguide` states what the documents say; a role
of `review` states what the implementation found, and it overrides the first. `scripts/knowledge
verify-structure` is the gate that keeps the two apart.

## Start of a phase: run these two

```bash
scripts/knowledge --origin note --brief        # what the implementation found
scripts/knowledge --section conflicts --brief  # what two documents still disagree about
```

They are different sets and you need both. The first is every note: the places where a plan's Global
Constraints may assert as settled something the implementation found to be otherwise. The second is every
recorded design-vs-styleguide contradiction — a resolved one prints `[overridden by notes/…]` on its location
line, and one with no such tag is **still open**. `[cited by notes/…]` is a different tag and not a weaker
one: it says a note leans on that rule, and the rule stands unchanged. **Today both exit 1** ("the notes tree
carries only…", "the Conflicts section holds no entry"): that is the honest answer — no notes written, no
design/styleguide harvest — not a broken tool. Run them anyway; they start answering the day a note or a
harvest lands.

Different filters AND together; multiple values inside one filter OR. So `--req A --req B --topic headers`
means "(cites A or B) and is in a headers file".

## Using the corpus while brainstorming a roadmap phase

A phase is scoped before it is planned, and scoping is the one moment where the *absence* of knowledge
matters more than its presence. Six steps, in order:

1. **Name the subsystems.** For each prefix the phase will touch: `scripts/knowledge --prefix-info HTTP` —
   subsystem, owning `docs/product-spec/NN` chapter, ID count and MUST/SHOULD/MAY split, all derived from
   appendix C. Works with or without a corpus.
2. **Find the holes.** `scripts/knowledge --gaps HTTP,PAGE` (or `--gaps all`) lists the IDs with no
   substantive entry, roll-up-only and uncited kept apart. Those are the requirements the phase must read out
   of the specification itself; budget for it, and say so in the design doc. (Today 30 IDs are uncited —
   `BODY-6/7`, `IO-6`, `IO-32..35`, `RECOV-17..34`, five `SEAM` — and `--gaps` names appendix C as their only
   normative statement.)
3. **Read what is contested.** `--section conflicts --brief` and `--origin note --brief`, narrowed to the
   same prefixes with `--prefix`. An open conflict inside a phase's scope is a decision the phase owns, not an
   assumption it inherits.
4. **Inherit from the phases you depend on.** `scripts/knowledge --phase 5a --brief` collects every
   requirement ID the `docs/work/*/phase5/phase5a/*.md` documents cite and queries all of them at once,
   printing which document contributed which IDs. It exits 0 with a message while a phase has no documents.
5. **Paste IDs and keys, never entries.** The design doc gets `PAGE-11`, `pagination/81881061` and the
   `<sub>` citation — an identifier the reader can re-resolve. A pasted entry body is a copy that goes stale
   silently, and it doubles the document.
6. **Write a note only for a finding.** Brainstorming produces intentions; a note records what the
   implementation *found* to be false about a harvested rule. If nothing has been implemented yet, there is
   nothing to note — the output of this step is the design doc, not `notes/`.

## Check the result is real before trusting it

**A `--req` hit is not proof the corpus knows anything.** Appendix B is the conformance-test checklist, and
its entries roll several IDs into one "the suite verifies X, Y, Z" sentence that states none of them. The CLI
tags these `[appendix-B roll-up]` and prints a WARNING when every hit is one. (`--coverage` reports the
substantive / roll-up-only / uncited split per prefix and `--gaps <PREFIX>` lists the IDs; run one rather
than trusting a remembered number.)

**A spec-only hit is not the .NET answer either.** Until the design role is harvested, a `--req` result says
what the specification requires, never how this port maps it. For the mapping, read the owning
`docs/sdk-design-dotnet/NN-*.md` section directly (grep it for the bold ID, `**RETRY-5**`).

### The roll-up path

1. `scripts/knowledge --req <id>` came back all roll-up (or empty).
2. Get the canonical text:

   ```bash
   grep -n '^| HTTP-10 ' docs/product-spec/appendix-c-consolidated-normative-requirement-index.md
   ```

   The leading `| ` and the trailing space are load-bearing — `grep 'HTTP-1'` matches HTTP-10 through
   HTTP-19.
3. Read the owning chapter. Ask the tool which one it is rather than a table:
   `scripts/knowledge --prefix-info HTTP` prints the subsystem cell and the matching
   `docs/product-spec/NN-*.md` chapter, both derived from appendix C at runtime.

## Two entry points

**ID-first — you have requirement IDs.** This is the plan-task case. Plan tasks list their IDs in the task
header; pass the whole set in one call, never six.

1. `scripts/knowledge --req HTTP-13,HTTP-14,HTTP-15` — what the corpus concluded. Once the design role is
   harvested, design-role entries quote `docs/sdk-design-dotnet/` inline and `--role design` isolates them;
   today, read the design chapter for the .NET mapping.
2. `grep -n '^| <ID> ' docs/product-spec/appendix-c-…md` — canonical text, when the query came back a roll-up
   or you need the normative wording verbatim.

**Topic-first — you have an area, or a styleguide citation.**

```bash
scripts/knowledge --list-topics                    # topics, entry, ID and note counts
scripts/knowledge --topic pipeline --section rules --brief cursor fork
```

**Every styleguide-derived topic carries no requirement ID at all** — once harvested, `data-modeling`'s
styleguide half, `naming-conventions`, `assertions`, `testing`, `csharp-idioms` and the rest. ID-first cannot
reach them. `--list-topics` shows which (today: none — every seeded topic carries IDs); don't work from a
memorised list.

For "styleguide 9.4" / "ch09", use `--chapter`. The styleguide is vendored at `docs/styleguide/csharp/`, whose
chapters are `01-formatting-and-tooling`, `02-naming-conventions`, `03-nullability-and-the-type-system`,
`04-variables-and-declarations`, `05-methods-and-functions`, `06-types-and-data-modeling`,
`07-csharp-idioms`, `08-error-handling`, `09-concurrency`, `10-api-design`, `11-testing`,
`12-project-organization`, `13-resource-management`, `14-documentation`, `15-performance`. Where this SDK
departs from a styleguide rule (the `I` prefix and `Async` suffix, for one), `docs/styleguide/README.md`'s
SDK overlay says so — check it before reporting a violation.

```bash
scripts/knowledge --chapter 9 lock              # styleguide 9.x → the concurrency chapter (after a harvest)
```

Entries record a chapter file and line range, never a section number, so `--chapter 9.4` queries chapter 9
and tells you it dropped the `.4`. Narrow with bare words instead. Until the styleguide is harvested, open
`docs/styleguide/csharp/09-concurrency.md` directly.

## Auditing: the one case where a broad query is right

A lookup wants the smallest answer. An audit wants a **complete group of rules**, because a rule it never
read is a rule it never checked. The CLI applies no cap, so a group query is complete as soon as the group is.

```bash
scripts/knowledge --topic api-design,http-domain-model,error-handling --section rules --brief
scripts/knowledge --prefix HTTP --section rules --brief
```

`--prefix` takes a whole ID family and is validated against appendix C, so a typo fails loudly instead of
returning nothing.

**One topic is not a group.** A search of `Rules` for the word "public" hits a dozen topics; an audit that
queries `api-design` alone reports clean over an incomplete set. Use the recorded groups, and extend this
table rather than improvising a group per audit — an audit is only repeatable if its group is written down.

**Read the coverage line before counting what came back.** `--section rules` returns the entries *filed as
rules*, and an entry's section is a per-ID filing decision, so a prefix with 38 canonical IDs can come back
with 36 (`CFG-14` and `CFG-29` are filed under `Reference`). The query says so itself — a `NOTE:` footer
naming every canonical ID the filters did not cover, and whether the corpus carries it in another section
(read it with `--req`) or nowhere at all (`--gaps`). Never take the entry count as the prefix's ID count.

Status: **live** — the query answers from the seeded spec role today; **half live** — the `--prefix` query is
live, the topic/chapter query waits on the design/styleguide harvest; **pending harvest** — nothing to query
yet, use the `Today` column.

shell, so the encoding row keeps its narrowing outside the table: run that group and then add
`--grep 'encoding|UTF-8|BOM|byte'` to it.

Otherwise grep the corpus for the subject word (`scripts/knowledge --section rules --brief <word>`), take the
topic files that came back, and add the row here before running the audit. A full `--section rules` group
runs to hundreds of entries and thousands of tokens; budget for it.

### The audit loop

1. **Read the notes first** — the phase-start query above. A rule that already carries a note is already
   known-broken; don't re-report it. A harvested entry that prints `[overridden by notes/…]` is the same
   signal inline. `[cited by notes/…]` is not that signal — it marks a rule a note **rests on**.
2. **Read the group.** One query, `--section rules`, from the table above.
3. **Check the system** against each rule.
4. **Write a note for each broken rule**, in `docs/knowledge/notes/<topic>.md`, naming the rule by the key
   the query printed (`retry-and-resilience/07534e67`). Backtick the key: that is how the CLI links the two,
   and `scripts/knowledge --key retry-and-resilience/07534e67` resolves it. The key changes exactly when the
   rule's text changes — including on a re-harvest that rewords it, which is when the note needs revisiting;
   `scripts/knowledge drift` reports a citation that has gone stale, and `scripts/knowledge
   verify-structure` fails on one. Never edit the harvested entry.
5. **Say which relation each key carries.** Put a relation verb — **Supersedes**, **Resolves**, **Answers**,
   **Narrows**, **Corrects**, **Overrides**, **Replaces** — immediately before the key or keys it governs,
   and those print `[overridden by notes/…]`. **Every other backticked key in the entry prints `[cited by
   notes/…]`**, which is what a rule the note *rests on* should say; write those with a leaning verb (`Adds
   to`, `Beside`, `Relates to`) or no verb at all. Get this wrong in the overriding direction and every later
   query reads a correct, load-bearing rule as overruled.

A note's shape: a topic heading, a section, one bullet, role `review`, a source path, a manual
`sha:manual-<slug>` marker.

```markdown
# retry-and-resilience — notes

Hand-written. `../harvested/retry-and-resilience.md` is what the documents say; this is what the
implementation found, and it wins.

## Superseded
- **What we found**, superseding `retry-and-resilience/07534e67`. …
  <sub>review · `docs/work/mvp/phase3/2026-10-01-phase3-retry-design.md` · high · sha:manual-3-erratum</sub>
```

Which section: `## Superseded` when following the harvested rule would cause damage, `## Conflicts` when you
are recording which of two documents won, `## Reference` when the note only points somewhere. A note is not
for a preference. Create `notes/<topic>.md` on the first note for that topic; `notes/.gitkeep` holds the
directory until then.

**Harvesting.** Always `--corpus docs/knowledge/harvested`; the skill's default is `docs/knowledge/`, which
no query reads and the structure gate rejects. The first harvest replaces the seeded tree wholesale,
`SOURCES.md` and `INDEX.md` included, and should cover all three roots (`docs/product-spec/`,
`docs/sdk-design-dotnet/` 00–09, `docs/styleguide/csharp/`) — never the registers (`sdk-design-dotnet`
10–12, `docs/deviations.md`, `docs/first-release.md`). If the harvest emits a `supersede` resolution, move it
to `notes/` by hand — a `## Superseded` entry under `harvested/` fails the gate.

## Never read a whole topic file

A filtered query answers the question for a fraction of the tokens, and `grep` is not a substitute — it has
no section, role, or exact-token ID matching. Two exceptions, both narrow:

- **An unnarrowed `--topic` costs more than the file.** Add `--section`, `--chapter`, or bare words, or read
  the file — but don't run a bare `--topic` on a subsystem topic (audit groups and topics `--list-topics`
  shows to be tiny excepted).
- **Following up a located entry, when you need the exact bytes.** The bullet sits at the printed line; read
  from it to the next `<sub>`, and stop at the section boundary. Prefer `--req` on the ID cluster (appendix C
  numbers related requirements together) or `--topic X --section rules`.

| Flag | Effect |

| `--prefix HTTP` | A whole ID family. The audit filter; validated against appendix C. |
| `--key pagination/81881061` | The one entry with that key. An unknown key means the rule was reworded. |
| `--origin harvested\|note` | Which tree. `note` is the phase-start query. |
| `--topic pipeline,retry` | Topic files by substring — matches broadly and silently. |
| `--section rules,…` | rules, constraints, conclusions, reference, conflicts, superseded (case-insensitive). |
| `--role spec\|design\|styleguide\|review` | Provenance role. `review` only ever appears in `notes/`. Today only `spec` has entries. |
| `--chapter 9` | Styleguide chapter. The only way in from a "styleguide N.M" citation (after a harvest). |
| `--grep <regex>` / bare words | Case-insensitive; `--grep` is a .NET regex, bare words are literal. |
| `--phase 5a` | Every ID cited by `docs/work/*/phase5/phase5a/*.md`, queried as one `--req` set, per-document breakdown first. A cited range (`HTTP-1–HTTP-35`, `HTTP-1-HTTP-35`, `HTTP-1..35`, each also with its endpoints in backticks or bold, which is how `docs/work/` mostly writes them: `**HTTP-1**–**HTTP-35**`) counts every appendix-C ID between its ends; a bare number that cannot close a range (`RETRY-12-3 times`) names nothing. Exits 0 with a message when the phase has no documents yet. |
| `--gaps HTTP` / `--gaps HTTP PAGE` / `--gaps HTTP,PAGE` / `--gaps all` | Canonical IDs with no substantive entry: roll-up-only and uncited apart. The pointer is checked against the chapters: an ID no `docs/product-spec/` chapter states is reported as **appendix C only**, with the `grep` line. **Answers without a corpus.** |
| `--prefix-info HTTP` | One prefix only (a second word exits 2). Subsystem, owning chapter, ID count and level split, from appendix C. **Answers without a corpus.** |
| `--brief` | Drop `<sub>` lines, ~30% smaller — but you lose the citation. |
| `--json` | Records, each with `origin`, `key` and a `rollup` boolean (snake_case fields). |
| `--list-topics` | Every topic with entry, distinct-ID and note counts. |
| `--list-reqs` | ID → location map. Large. Prefer `--coverage`. |
| `--coverage` | Substantive vs roll-up-only vs uncited, per prefix. A report, not a gate. |
| `--no-drift-check` | Skip the stale-source warning (below). |
| `--root DIR` | Query another checkout (or set `KNOWLEDGE_ROOT`). Default: the checkout the tool was built from. |
| `verify-structure` / `drift` | The gate (exit 0/1/2) and the report (always 0 unless it cannot run). |

Zero matches exits 1 and names what does exist — nearest IDs, available topics, harvested chapters. Follow
it rather than guessing again. A typo in `--role`, `--section`, `--chapter`, `--origin`, `--prefix`, `--gaps`
or `--prefix-info`, an unknown flag, or a missing flag value exits 2. `--help` for the rest.

**Stale-source warning.** When a result derives from a source file whose sha no longer matches the one
`harvested/SOURCES.md` recorded, the CLI prints `warning: stale <path> …` on **stderr** and carries on. It is a
hint, never a failure: the entries describe an older revision of that document, so check the document before
acting on a surprising one. `--no-drift-check` silences it; `scripts/knowledge drift` is the full report.

## Citing what you find

The `<sub>` line is the citation. Every source this repository harvests is **repo-relative** — the product
spec, the design document, and the styleguide, which is vendored under `docs/styleguide/` — so paste the
path exactly as printed:

- `` docs/product-spec/09-retry-and-resilience.md:11-11 · sha:9efbe276001e ``
- `` docs/styleguide/csharp/09-concurrency.md:40-52 `` (once the styleguide is harvested)

There is no machine prefix to strip. (The Ruby port harvested its styleguide by absolute path from a sibling
repository and had to trim `/home/…/styleguide/` before committing a citation; vendoring removed that step
here. A citation you copy from a sibling SDK's corpus via `--root` may still carry one — trim it, and prefer
the vendored path.)

Shape is not uniform: Conflicts entries carry two sources and no sha; a note carries a manual `sha:` marker
and sometimes no line range. Copy what is there, don't assume four fields. Drop `--brief` whenever the result
will be cited.

## Common mistakes

| Mistake | Fix |
|---|---|
| Reading an exit 1 from `--role design`, `--chapter N` or `--section conflicts` as "the documents say nothing" | Only the spec role is seeded. Read `docs/sdk-design-dotnet/` or `docs/styleguide/csharp/` directly until a harvest lands. |
| Taking a spec-only `--req` hit as the .NET design | It is the requirement, not the mapping. Grep the design chapter for `**<ID>**`. |
| Editing an entry under `harvested/` to record what you found | Write a note in `notes/` naming the rule by its key. The harvested sha is per-file; your edit is invisible to the next harvest and the gate rejects it. |
| Trusting a `--req` hit that is all roll-up | Watch for the WARNING; follow all three steps of the roll-up path. |
| Six sequential `--req` calls for one task | One comma-separated call — or `--phase N` when the IDs are a phase's. |
| Auditing one topic and reporting "clean" | One topic is not a group. Use the group table, or `--prefix`. |
| ID-first on `naming-conventions` / `testing` / `csharp-idioms` (after a harvest) | Those carry zero IDs. Topic- or chapter-first. |
| Reporting an `I`-prefix or `Async`-suffix "violation" from the styleguide | Check the SDK overlay in `docs/styleguide/README.md` first — the departure is deliberate. |
| `--topic X` with nothing else | Not a filter; costs more than the file — unless `--list-topics` shows the topic is tiny. |
| Copying a whole entry into a design doc | Cite the ID, the key and the `<sub>`. A copied body goes stale with no signal. |
| Searching for the word "drift" or "verify-structure" as a bare word | The first word selects a subcommand. Use `--grep drift`. |
| Treating `--coverage`, `--gaps` or `scripts/knowledge drift` as a gate | Hand-run reports. The only gate is `scripts/knowledge verify-structure`. |
