- **A `[LoggerMessage]` source generator orders the classes of one assembly differently from one build to the next, so an assembly holds at most one type with generated log methods, and a run count cannot prove the fix.** `Microsoft.Extensions.Logging.Generators` writes every `[LoggerMessage]` partial class of an assembly into one `LoggerMessage.g.cs` and, in 10.0.14, emitted `Dexpace.Sdk.Http.SystemNet`'s two (`HeaderDropLog`, `ProxyWarnings`) in an order that varied between compilations (eight builds with `EmitCompilerGeneratedFiles` gave two different files, six to two). The generated text reaches the PDB (`EmbedUntrackedSources`) and, through the PDB checksum, the DLL, so two packs of one commit differed by 72 bytes (the MVID, the CodeView GUID, the PE time stamp, the PDB checksum) about one run in five. This, not the SDK patch level phase 11 suspected, was the `reproducible packages` job's red. The fix is to give the generator one class to order (`TransportLog`), held by `LoggerMessageDeterminismArchitectureTests`; the proof is one distinct `LoggerMessage.g.cs` hash across repeated builds (V7), because a nondeterminism that fires one run in five passes four of five green runs by itself.

- **A strong-name key must be a `CALG_RSA_SIGN` blob, a signed friend assembly demands a keyed `InternalsVisibleTo`, and the .NET SDK has no cross-platform `sn -p`.** `Dexpace.Sdk.snk` is a 2048-bit RSA PRIVATEKEYBLOB written from `RSA.ExportParameters(true)`: `07 02 00 00`, `00 24 00 00` (`CALG_RSA_SIGN`), `52 53 41 32` (`RSA2`), the bit length, then the public exponent, modulus, P, Q, DP, DQ, InverseQ and D, all little-endian. The same key as `AssemblyOriginatorKeyFile` exported as `CALG_RSA_KEYX` (`00 A4 00 00`) builds to `CS0281`. The public key that goes in `InternalsVisibleTo Key=` is `00 24 00 00 04 80 00 00`, the length, then a PUBLICKEYBLOB (`06 02 00 00 00 24 00 00 52 53 41 31`, bit length, exponent, modulus), so `DexpacePublicKey` is the one hex property every library reads; the `PublicKeyToken` is the last eight bytes of the SHA-1 of that blob, reversed (`fb3fcc3028a3989e`). Once a test assembly is signed, a keyless `InternalsVisibleTo` to it is `CS1726`, which is why signing is scoped to `src/` and `tests/` and the tools, whose grants are keyless, stay unsigned. Strong naming is an assembly identity, not a security measure on .NET; the key is committed because nothing trusts it.

- **nuget.org repository-signs every package, so "byte-identical to the published artifact" (`NFR-12`'s release half) is read modulo the signature.** The package on nuget.org carries a `.signature.p7s` entry the pushed file did not, which rewrites the zip directory, so no whole-file digest of the two can match.
