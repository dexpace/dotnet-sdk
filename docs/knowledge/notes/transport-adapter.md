# transport-adapter — notes

Hand-written. `../harvested/transport-adapter.md` is what the documents say; this is what the implementation found, and it wins.
Facts measured on .NET SDK 10.0.401 / runtime 10.0.12, Linux, against a raw `TcpListener` peer and the phase 8a conformance kit's
loopback fixture, so a later reader does not have to re-measure them.

## Conclusions
- **`SocketsHttpHandler` fails the whole response on a malformed response header name, but passes a control byte in a value, so `TRANSPORT-14`'s name half cannot be met by the reference transport's adapter.** A header name with a space, a control byte or a non-ASCII byte raises `HttpRequestException` ("Received an invalid header name") from the native client before `SystemNetHttpClient` sees any header; a control byte in a header *value* reaches `HttpResponseMessage.Headers`, where `Headers.Builder.AddInbound`'s per-header drop handles it, and obs-text in a value is preserved (`TRANSPORT-14`'s SHOULD). The kit asserts the three clauses separately (`transport-14.value-control-dropped`, `transport-14.obs-text-preserved`, `transport-14.name-malformed-dropped`) so a transport that cannot meet the name clause waives that one assertion alone, and the reference transport's name-clause failure is waived with Owner `8b`, who dispositions it (a design §10 entry if no handler-level workaround exists).

- **A cancellation the caller did not request reaches the adapter as a `TaskCanceledException` whose inner exception tells the causes apart: `IOException` for `HttpClient.CancelPendingRequests()` and `HttpClient.Dispose()`, `TimeoutException` for `HttpClient.Timeout`.** The shapes are identical on `SendAsync` and `Send`. `SystemNetHttpClient` maps every `OperationCanceledException` the caller did not request to a retryable `ServiceRequestTimeoutException`, so a borrowed client cancelled from inside is reported as a retryable timeout, which `TRANSPORT-8` forbids (`transport-8.internal-cancel-is-terminal` fails on it, waived with Owner `8b`). The discriminator phase 8b needs is the state it owns (its per-call deadline, the caller's token) first and `InnerException is TimeoutException` second. *Resolved 2026-10-11 (phase 8b):* `SendFailures` classifies by that order, and an internal cancellation is a new, terminal `OperationCanceledException` with the native exception on its `ExceptionTrail` (not `InnerException`: see the G8 entry below).

- **`SocketsHttpHandler` has no switch for its own connection-failure retry and re-sends a request with no content whose connection ends before any response byte up to three more times inside one `SendAsync`, on a pooled connection and on a brand-new one; a reset is not re-sent, and a single-use body it already wrote is never re-written.** The trigger is exact (runtime 10.0, `HttpConnection.SendAsync`): `_canRetry` is cleared on every send and set only when the first read for the response returns zero bytes on a request with no content, and an `IOException` becomes `RetryOnConnectionFailure` only while it is set, so a read that fails with `ECONNRESET` is `NoRetry`. Against a peer that reads each request and then closes in order (an empty reply that closes: a FIN, no reset), a `GET`, a `DELETE` and a body-less `POST` each reached the server four times and surfaced as one `HttpRequestException (ResponseEnded)` on every run, sequential, on one core and in 32 processes in parallel; against a bare reset (a zero-linger close with no shutdown) each reached it once, as `IOException` over `SocketException (ConnectionReset)`; a `POST` with a byte body reached it once (`HttpIOException (ResponseEnded)`, and `SerializeToStreamAsync` ran once, which is what `TRANSPORT-2`'s spec sentence needs). The kit's `LoopbackResponse.Abort` is neither: disposing the server's `TcpClient` shuts its stream down before the zero-linger close, so a FIN precedes the reset (a raw peer reads zero bytes, then finds `EPIPE` in `SO_ERROR`, the error Linux records for a reset in `CLOSE_WAIT`). Linux reports the FIN to every read, because `tcp_recvmsg` checks `SOCK_DONE` before the socket error; macOS checks `so_error` first in `soreceive` (from the XNU source, not measured here), so a read that starts after the reset landed fails and is not re-sent: the macOS CI counted one arrival and then two where Linux counts four, and `transport-2.bodyless-not-resent` therefore closes in order. On a fresh connection a plain `HttpClient` over two aborts then a success returned the 200 from one `SendAsync` (three requests at the server) and over four aborts threw. Through `SystemNetHttpClient` and `DexpacePipeline.CreateDefault` with `MaxRetryAttempts = 0`, one SDK attempt was four wire sends. So the retry the SDK pipeline is meant to own alone is not off, `TRANSPORT-2`'s MUST ("disable it") is unmet by the reference transport for any request without content, and a kit script has to answer by the pipeline's attempt number, not by its own request count: `transport-20.retried-by-the-pipeline` resets every arrival of the first attempt, because "reset the first two" can be delivered by the native retry inside one attempt and the pipeline never retries. The assertion that sees the retry is `transport-2.bodyless-not-resent`, waived for the reference transport with owner 8b on every platform (*phase 8b, 2026-10-11:* now a permanent waiver after the partial fix recorded in the body-less-retry entry below); the earlier readings of this fact ("once", "two aborts in a row surface as `HttpRequestException`", and "re-sent after a reset") were wrong and are replaced here.

- **A non-numeric `Content-Length` on a `Connection: close` reply is tolerated and the body reads to the close; the transport reports `ContentLength == -1`.** The raw `HttpClient.GetAsync` buffers by default, so `Content.Headers.ContentLength` then reads the buffered length (5 in the probe); `SystemNetHttpClient` sends with `ResponseHeadersRead`, so the adapter sees no length and `ResponseBody.ContentLength` is `-1`, which `transport-27.inbound-downgrade` asserts. A `520` with a body is delivered as status 520 with a readable body, and a body-less `POST` goes out with `Content-Length: 0` while a `GET` carries neither a length nor a transfer coding.

- **A pooling client releases a connection by returning it to its pool, not by closing it, so "the client released this connection" is only observable server-side through reuse or a close, and a pool reuses its newest idle connection first.** The kit's `WaitForConnectionReleasedAsync` therefore completes on a close or on a further request on the connection, and a release check on a pooled response sends a burst of concurrent probe requests through the transport (as many as there are connections) until the connection shows up; a connection still held by a leaked response is never reused however many probes are sent. A single sequential probe is not enough: with two idle connections it reuses the newer one forever and the older one never shows. A release check after a reply the *server* closed (`Connection: close`) proves nothing, so the fixture records which side closed first and the check refuses it.

- **A leaked socket is closed by its finalizer once it is garbage, so a negative control that leaks a connection must keep what it leaked reachable.** A control that discarded a `Response` without disposing it "released" the connection between garbage collections in about one full run in five, and the control passed when it must fail. The leak controls root what they leak (`Leaks.Root`), and the owned `SystemNetHttpClient(ILogger)` constructor, which built its handler with the default proxy and so honoured `HTTP_PROXY`, was kept off the environment in the conformance driver by pinning `HttpClient.DefaultProxy` to direct once, because the internal constructor that pins `UseProxy = false` took no logger. *Phase 8b (2026-10-11) removed the cause and the pin:* the owned handler has `UseProxy = false` unless a `ProxyOptions` is given, and `HttpClient.DefaultProxy` is banned in `src/`.

- **`HttpClient.Send` over a handler that implements only `SendAsync` throws `NotSupportedException`, and over a `DelegatingHandler` that overrides only `SendAsync` it silently skips that handler.** Measured on 10.0.401: the first message is "The synchronous method is not supported by '…'. If you're using a custom 'HttpMessageHandler' and wish to use synchronous HTTP methods, you must override its 'Send' virtual method"; the second request succeeds with the delegating handler's `Ran` count at 0, because `DelegatingHandler.Send` forwards to the inner handler's `Send`. A real synchronous `SystemNetHttpClient.Execute` therefore makes a hand-written `SendAsync`-only handler either loud (primary) or invisible (delegating), recorded as the `sync-borrowed-handlers` asymmetry in `docs/first-release.md`.

- **Cancelling and disposing the token given to `SendAsync(…, ResponseHeadersRead, token)` after it returned does not cut a body read already under way, and both faces report `CancelPendingRequests`, `Dispose` and `HttpClient.Timeout` with the same shapes.** A gated second chunk still arrived after the source was cancelled and disposed, so a per-call deadline source may be disposed when `SendAsync` returns and bounds the exchange until the response headers, like `AttemptTimeout`. `CancelPendingRequests` and a `Dispose` mid-call give `TaskCanceledException` over `IOException` on `SendAsync` and `Send` alike, `HttpClient.Timeout` gives it over `TimeoutException`.

- **Through a forward proxy that answers `407 Proxy-Authenticate: Basic`, `SocketsHttpHandler` asks the proxy's `ICredentials`, sends the request again and serialises the content twice, on every `http://` request (the challenge is not cached); an `https://` target is challenged at the `CONNECT` and never serialises the content.** The origin's later `401` is not answered with any credential while the handler's own `Credentials` are unset. Measured with the 8a fixture as the proxy: two serialisations per `POST` for each of two requests on one keep-alive connection, and zero serialisations when the `CONNECT` itself gets a `407`. This is the native re-send `TRANSPORT-18` binds, and why a bounded capture (not a refusal) is the answer where the native layer can re-send.

- **`RetryFacts.IsRetryableCause` calls any `IOException` anywhere in a failure's cause chain retryable, and the runtime's internal cancellation is a `TaskCanceledException` over an `IOException`.** An `OperationCanceledException` that kept the native one as its `InnerException` would therefore be retried, so a terminal internal cancellation carries the native exception on `ExceptionTrail.AddSuppressed` instead, where diagnostics find it and the classifier does not look. A cancellation the caller requested is likewise rebuilt to carry the caller's own token when a linked deadline token made the native one carry another.

- **For a SOCKS proxy `SocketsHttpHandler` asks `ICredentials.GetCredential(proxyUri, authType)` once per connection with `authType` equal to the proxy URI scheme (`socks5`, `socks4`, `socks4a`), not `Basic`; the SOCKS5 answer drives the username/password sub-negotiation, and `socks4` resolves the destination host locally.** A raw listener saw `05 02 00 02` (offering username/password) then `01 01 'u' 01 'p'` for the pair, and a SOCKS4 greeting with the user id only (hostname form for `socks4a`). `ProxyOptions.FromEnvironment` maps `socks4a` to `ProxyType.Socks4`, so a SOCKS4a proxy is reached through `socks4://` and the destination is resolved locally.

- **`HttpClient` wraps an `IOException` or `InvalidOperationException` thrown by content serialisation in an `HttpRequestException`, on `Send` and `SendAsync` alike (`HttpContent.CopyTo[Async]` does too), and leaves a `NotSupportedException` or an `SdkException` such as `StreamConsumedException` unwrapped.** A refused re-send of a single-use body therefore has to be an `IOException` carrying the `StreamConsumedException`, or it would escape the transport's `HttpRequestException` filter as a raw SDK exception; the chain is `ServiceRequestException` → `HttpRequestException` → `IOException` → `StreamConsumedException`. A request-header collection refuses only content-kind headers: a response-kind header (`ETag`, `Retry-After`, `Server`) is accepted there as a custom header, so the reachable "refused by the native collection" case is a content header on a request with no content to carry it.

- **The native connection-failure retry is switched off by the request having content: a body-less `POST`, `PUT`, `PATCH` or extension method given a zero-length `ByteArrayContent` reaches the server once, byte for byte the same wire; `GET`, `HEAD`, `OPTIONS`, `DELETE` and `TRACE` still arrive four times, and an `Expect: 100-continue` brings the retry back.** On a peer that reads each request and closes in order, with null content, `GET`, `HEAD`, `OPTIONS`, `DELETE`, `TRACE`, `POST`, `PUT`, `PATCH` and an extension verb each arrived 4 times; with `new ByteArrayContent([])` every one arrived once, except `POST` with `Expect: 100-continue`, which arrived 4 times. `HttpMethod` frames `Content-Length: 0` for null content on every method except `GET`, `HEAD`, `OPTIONS`, `DELETE` and `CONNECT` (`TRACE` included, measured), so an empty content is wire-identical exactly there; on `DELETE` and `OPTIONS` it would add a `Content-Length: 0` the native client does not write. `CONNECT` is refused by `HttpClient` without a host. The runtime reads (10.0): `_canRetry` is cleared on every send and set only when the first read returns zero bytes and the request has no content or an `Expect: 100-continue`. `TRACE` is left without content on purpose (RFC 9110 section 9.3.8, `TRANSPORT-26`), a decision recorded in design §10 entry 33.

- **A pool-backed barrier of 64 participants (`Parallel.For` over `Barrier.SignalAndWait`) starves the thread pool for tens of seconds and pushes a 50-iteration conformance race past its 20 s bound.** The project-wide run then failed `transport-9.settle-race-releases` on one subject and passed on the other; the race itself was innocent. Release a crowd of concurrent callers from dedicated threads (`TaskCreationOptions.LongRunning` and a `ManualResetEventSlim`), never a barrier sized above the pool's minimum.

- **A per-call default deadline armed by the transport is a bound on top of a borrowed `HttpClient`'s own `Timeout`, not a replacement for it, so "the 100 s default replaces `HttpClient.Timeout`" is true only of a client the transport builds.** `CallDeadline.Effective(options, _settings.Timeout)` runs for every construction, and a borrowed client's `Timeout` is untouched (the shared client is never mutated), so the shorter of the two cuts a call: a borrowed client with an infinite or five-minute `Timeout` and a server that takes 120 s to send headers succeeded on `main` and fails after 8b with a retryable `ServiceRequestTimeoutException`, which a pipeline re-sends. A design that says the default leaves "no behaviour changed" has to say it for the owned construction only, and give the borrowed one a migration (`SystemNetHttpClientOptions { Timeout = null }` or a longer `RequestOptions.Timeout`); a fake clock pins it without waiting (`DeadlineTests`).

- **`IHttpClientFactory`'s default chain follows redirects, composes with the 8b handler constructor once the primary has redirects off, and never releases a handler whose lifetime is infinite.** The default chain is `LifetimeTrackingHttpMessageHandler -> LoggingScopeHttpMessageHandler -> LoggingHttpMessageHandler -> SocketsHttpHandler` with `AllowAutoRedirect = true`, so `new SystemNetHttpClient(factory.CreateHandler(name))` throws naming `AllowAutoRedirect`; with `ConfigurePrimaryHttpMessageHandler` building `SystemNetHttpClient.CreatePrimaryHandler`, `RemoveAllLoggers()` and a caller's `AddHttpMessageHandler`, the chain is `LifetimeTracking -> <caller's handler> -> SocketsHttpHandler` and the check walks it to the primary (phase 9 V3). A transport that holds one chain for the process needs `SetHandlerLifetime(Timeout.InfiniteTimeSpan)`, and then the factory never releases the handler: the kit's `transport-15.owned-released` failed over the DI-built transport until a container-owned lease disposed the primary the package created (V8).
