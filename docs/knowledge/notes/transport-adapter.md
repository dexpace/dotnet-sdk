# transport-adapter — notes

Hand-written. `../harvested/transport-adapter.md` is what the documents say; this is what the implementation found, and it wins.
Facts measured on .NET SDK 10.0.401 / runtime 10.0.12, Linux, against a raw `TcpListener` peer and the phase 8a conformance kit's
loopback fixture, so a later reader does not have to re-measure them.

## Conclusions
- **`SocketsHttpHandler` fails the whole response on a malformed response header name, but passes a control byte in a value, so `TRANSPORT-14`'s name half cannot be met by the reference transport's adapter.** A header name with a space, a control byte or a non-ASCII byte raises `HttpRequestException` ("Received an invalid header name") from the native client before `SystemNetHttpClient` sees any header; a control byte in a header *value* reaches `HttpResponseMessage.Headers`, where `Headers.Builder.AddInbound`'s per-header drop handles it, and obs-text in a value is preserved (`TRANSPORT-14`'s SHOULD). The kit asserts the three clauses separately (`transport-14.value-control-dropped`, `transport-14.obs-text-preserved`, `transport-14.name-malformed-dropped`) so a transport that cannot meet the name clause waives that one assertion alone, and the reference transport's name-clause failure is waived with Owner `8b`, who dispositions it (a design §10 entry if no handler-level workaround exists).

- **A cancellation the caller did not request reaches the adapter as a `TaskCanceledException` whose inner exception tells the causes apart: `IOException` for `HttpClient.CancelPendingRequests()` and `HttpClient.Dispose()`, `TimeoutException` for `HttpClient.Timeout`.** The shapes are identical on `SendAsync` and `Send`. `SystemNetHttpClient` maps every `OperationCanceledException` the caller did not request to a retryable `ServiceRequestTimeoutException`, so a borrowed client cancelled from inside is reported as a retryable timeout, which `TRANSPORT-8` forbids (`transport-8.internal-cancel-is-terminal` fails on it, waived with Owner `8b`). The discriminator phase 8b needs is the state it owns (its per-call deadline, the caller's token) first and `InnerException is TimeoutException` second.

- **`SocketsHttpHandler` has no switch for its own connection-failure retry and re-sends a request with no content whose connection ends before any response byte up to three more times inside one `SendAsync`, on a pooled connection and on a brand-new one; a reset is not re-sent, and a single-use body it already wrote is never re-written.** The trigger is exact (runtime 10.0, `HttpConnection.SendAsync`): `_canRetry` is cleared on every send and set only when the first read for the response returns zero bytes on a request with no content, and an `IOException` becomes `RetryOnConnectionFailure` only while it is set, so a read that fails with `ECONNRESET` is `NoRetry`. Against a peer that reads each request and then closes in order (an empty reply that closes: a FIN, no reset), a `GET`, a `DELETE` and a body-less `POST` each reached the server four times and surfaced as one `HttpRequestException (ResponseEnded)` on every run, sequential, on one core and in 32 processes in parallel; against a bare reset (a zero-linger close with no shutdown) each reached it once, as `IOException` over `SocketException (ConnectionReset)`; a `POST` with a byte body reached it once (`HttpIOException (ResponseEnded)`, and `SerializeToStreamAsync` ran once, which is what `TRANSPORT-2`'s spec sentence needs). The kit's `LoopbackResponse.Abort` is neither: disposing the server's `TcpClient` shuts its stream down before the zero-linger close, so a FIN precedes the reset (a raw peer reads zero bytes, then finds `EPIPE` in `SO_ERROR`, the error Linux records for a reset in `CLOSE_WAIT`). Linux reports the FIN to every read, because `tcp_recvmsg` checks `SOCK_DONE` before the socket error; macOS checks `so_error` first in `soreceive` (from the XNU source, not measured here), so a read that starts after the reset landed fails and is not re-sent: the macOS CI counted one arrival and then two where Linux counts four, and `transport-2.bodyless-not-resent` therefore closes in order. On a fresh connection a plain `HttpClient` over two aborts then a success returned the 200 from one `SendAsync` (three requests at the server) and over four aborts threw. Through `SystemNetHttpClient` and `DexpacePipeline.CreateDefault` with `MaxRetryAttempts = 0`, one SDK attempt was four wire sends. So the retry the SDK pipeline is meant to own alone is not off, `TRANSPORT-2`'s MUST ("disable it") is unmet by the reference transport for any request without content, and a kit script has to answer by the pipeline's attempt number, not by its own request count: `transport-20.retried-by-the-pipeline` resets every arrival of the first attempt, because "reset the first two" can be delivered by the native retry inside one attempt and the pipeline never retries. The assertion that sees the retry is `transport-2.bodyless-not-resent`, waived for the reference transport with owner 8b on every platform; the earlier readings of this fact ("once", "two aborts in a row surface as `HttpRequestException`", and "re-sent after a reset") were wrong and are replaced here.

- **A non-numeric `Content-Length` on a `Connection: close` reply is tolerated and the body reads to the close; the transport reports `ContentLength == -1`.** The raw `HttpClient.GetAsync` buffers by default, so `Content.Headers.ContentLength` then reads the buffered length (5 in the probe); `SystemNetHttpClient` sends with `ResponseHeadersRead`, so the adapter sees no length and `ResponseBody.ContentLength` is `-1`, which `transport-27.inbound-downgrade` asserts. A `520` with a body is delivered as status 520 with a readable body, and a body-less `POST` goes out with `Content-Length: 0` while a `GET` carries neither a length nor a transfer coding.

- **A pooling client releases a connection by returning it to its pool, not by closing it, so "the client released this connection" is only observable server-side through reuse or a close, and a pool reuses its newest idle connection first.** The kit's `WaitForConnectionReleasedAsync` therefore completes on a close or on a further request on the connection, and a release check on a pooled response sends a burst of concurrent probe requests through the transport (as many as there are connections) until the connection shows up; a connection still held by a leaked response is never reused however many probes are sent. A single sequential probe is not enough: with two idle connections it reuses the newer one forever and the older one never shows. A release check after a reply the *server* closed (`Connection: close`) proves nothing, so the fixture records which side closed first and the check refuses it.

- **A leaked socket is closed by its finalizer once it is garbage, so a negative control that leaks a connection must keep what it leaked reachable.** A control that discarded a `Response` without disposing it "released" the connection between garbage collections in about one full run in five, and the control passed when it must fail. The leak controls root what they leak (`Leaks.Root`), and the owned `SystemNetHttpClient(ILogger)` constructor, which builds its handler with the default proxy and so honours `HTTP_PROXY`, is kept off the environment in the conformance driver by pinning `HttpClient.DefaultProxy` to direct once, because the internal constructor that pins `UseProxy = false` takes no logger.
