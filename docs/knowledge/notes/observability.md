## Conflicts
- **The SDK's HTTP log events use `ILogger.Log<TState>` with a key/value record and `LoggerMessage.Define`, not the `[LoggerMessage]` source generator that styleguide 6.2 asks for.** Resolves the styleguide's 6.2 ("use the `LoggerMessage` source generator on hot-path log statements", `docs/styleguide/csharp-aspnetcore/06-logging-and-observability.md`) in favour of the SDK, and leans on `tooling-and-quality-gates/f7bf2569` (6.2 is enforced by CA1848, satisfied by the generator and by `LoggerMessage.Define` alike): `OBS-39` fixes OpenTelemetry-style keys such as `http.request.method` and `http.request.header.<name>`, and the generator binds placeholders to C# parameter names, so a dotted placeholder is rejected (`SYSLIB1014`). The two header-bearing events (`http.request`, `http.response`) carry a dynamic key set, one key per logged header, which no fixed template can express either, so they are written through `ILogger.Log` with an internal read-only list of key/value pairs that is built only after the level and `IsEnabled` checks (nothing is allocated when disabled, `OBS-1`). The fixed-key events (`http.instrumentation.log_failed`, `http.instrumentation.body_capture_failed`, `dexpace.dispose.suppressed`) use cached `LoggerMessage.Define` delegates, with a scoped `CA1727` suppression because the dotted placeholder names are the published state keys. `CA1848` did not fire on the direct `Log<TState>` call on SDK 10.0.401 (checked in phase 5b), and `CA1873` is satisfied by building the record into a local before the call. Phase 5b, P5b-3, open for the lead; the SDK overlay in `docs/styleguide/README.md` carries the row.
